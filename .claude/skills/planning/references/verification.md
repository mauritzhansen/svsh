# Verification Protocol

Run after all tasks in PLAN.md are committed. Writes `.cursor/plans/{feature}/VERIFICATION.md`. Goal-backward: verify the feature achieves its objective, not just that tasks were completed.

**Core principle: existence ≠ implementation.** A file existing does not mean the feature works.

---

## Four Levels (check in order)

| Level | Question | How to check |
|-------|----------|--------------|
| 1. Exists | Is the file present? | `ls {path}` |
| 2. Substantive | Is it real code, not a stub? | Check for placeholder text, empty returns, TODO, hardcoded values |
| 3. Wired | Is it connected to the system? | Check imports, usages, route registrations |
| 4. Tested | Does it behave correctly? | Run checks, grep for assertions, verify data flows |

A file that exists but is a stub = **Level 1 pass, Level 2 fail.**
A file that exists and has code but is never imported = **Level 3 fail (orphaned).**

---

## Stub Detection

These patterns indicate placeholder code regardless of file length:

```bash
# Comment stubs
grep -E "TODO|FIXME|placeholder|coming soon|to be implemented" {file}

# Empty implementations
grep -E "return null|return \{\}|return \[\]|=> \{\}" {file}

# Hardcoded values where dynamic expected
grep -E "dummy|sample|test data|lorem ipsum" {file}
```

---

## Wiring Checks

| Pattern | Check |
|---------|-------|
| Component → Store | Component imports store and calls load on mount |
| Component → Service | Component imports service and calls it on user action |
| Service → API | Service calls `api.get/post/patch` with correct endpoint |
| Save → Reconcile | Save calls `cacheWriteThrough.upsertRow` + store upsert after success |
| Route registered | New screen appears in `App.jsx` routes inside `FeatureRoute` |
| Feature flag | Route and nav entry guarded by `isFeatureEnabled(flagId)` |

---

## Test Quality Audit

- **Disabled tests** — `grep -E "it\.skip|test\.skip|xit\("` on test files. A disabled test linked to a must-have = that truth is not tested.
- **Circular tests** — Expected values generated by the same system being tested prove consistency, not correctness.
- **Assertion strength** — Check that assertions are value-level (`toEqual(expected)`) not just existence-level (`toBeDefined()`).

---

## Process

**1. Load must-haves** from PLAN.md (truths, artifacts, key links).

**2. Verify each truth** — is there evidence in the codebase that this behavior exists? Status: ✓ VERIFIED | ✗ FAILED | ? NEEDS HUMAN

**3. Verify each artifact** at all four levels. Status per level.

**4. Verify each key link** — does the wiring exist? Grep for the import and the call site.

**5. Scan for stubs** in files listed in PLAN.md tasks.

**6. Run test quality audit** on any test files created or modified. Skip this step if the plan did not create or modify test files.

**7. Determine overall status:**
- All truths VERIFIED + all artifacts pass Level 3 + all key links wired + no stub patterns → **passed**
- Any truth FAILED or artifact MISSING/STUB or key link NOT WIRED → **gaps_found**
- All automated checks pass but behavior requires human observation → **human_needed**

**8. Write VERIFICATION.md.**

**9. If gaps_found** — identify the gap, describe the fix, create a follow-up task list.
